Esqueleto §7 (execução — blocos):
- Cabeçalho: `Execução #<curta> — "<term>"`, `BDTD + CAPES · <data> · <total> resultados · [duração]`.
- Banner por estado: ok (verde, sem alarde) / parcial (âmbar: "CAPES não respondeu: resultados só da BDTD") / falha (vermelho + motivo + [repetir]) / cancelled ("Execução cancelada" + [executar novamente]).
- Carregamento: progresso por fonte ("buscando BDTD…"), cancelável. Diferencial de novos e cards ficam na fase 8 — aqui o terminal mostra placeholder "Resultados — lista na fase 8" (SEM fingir itens).

Contrato real (sem mudança):
- labApi.getRun(runId,{getToken}) → SearchRunDTO { id, searchId, status, termSnapshot, sourcesSnapshot, executedAt, startedAt|null, finishedAt|null, metrics:{perSource:{bdtd:{status:'ok'|'failed'|'skipped',total,returned,durationMs},capes:{...}}, newCount, coverage:{bdtd,capes}}, error:{code,message}|null }.
- labApi.cancelJob(runId,{getToken}) → POST /jobs/:id/cancel → SearchRunDTO (cancelled). Cancelar terminal (succeeded/partial/failed/cancelled) → servidor responde erro; botão some no terminal.
- Status de run: 'queued'|'running' (não-terminal) vs 'succeeded'|'partial'|'failed'|'cancelled' (terminal). Rótulos PT: queued "na fila", running "executando", succeeded "ok", partial "parcial", failed "falha", cancelled "cancelada".
- Progresso por fonte: sourcesSnapshot (fontes pedidas) × perSource.status — fonte com status 'skipped' → "pulada"; 'ok' com run running → "buscando…"; terminal → "<returned> itens · <durationMs>ms". JobDTO.progress NÃO é necessário (getRun já traz tudo).
- Duração: finishedAt−startedAt (ambos presentes) senão Date.now()−startedAt durante polling; ausentes → "—".
- Total: coverage.bdtd + coverage.capes. Novos desde anterior: metrics.newCount (badge "N NOVOS" só informativo aqui; lista na fase 8).
- Polling (discrição OpenCode concretizada neste plano): intervalo fixo 2500ms via setInterval; para em terminal, em 10 min (240 tentativas → banner erro "Acompanhamento excedido — reabra a tela"), e no unmount; cleanup do unmount LIMPA SÓ O TIMER, nunca chama cancel (D-08: run vive no servidor; voltar = novo mount retoma do getRun atual). Sem refresh manual (sem botão atualizar).
- Rota: apps/lab/app/project/[id]/run.tsx — query runId + searchId (para [repetir]/[executar novamente] = executeSearch(searchId, {idempotencyKey: randomUUID}) + replace runId). 401 → expired/next=`/project/${id}/run?runId=...`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| poll → getRun | runId vem da query (hostil); uuid inválido → banner local sem request; 404 alheio genérico |
| cancelar → POST cancel | Só o dono cancela (servidor owner-scoped); botão some no terminal (sem ação inválida) |
| motivo de falha → tela | error.message do servidor já é seguro para cliente (envelope PT-BR) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-03-01 | Denial of Service | polling agressivo | mitigate | 2500ms fixo + teto 240 polls + para em terminal; sem auto-retry após 3 erros seguidos |
| T-07-03-02 | Tampering | cancel de run alheio | mitigate | cancelJob owner-scoped no servidor; runId da query nunca autoriza nada no client |
| T-07-03-03 | Information Disclosure | runId na URL | accept | id opaco uuid sem dados; 404 idêntico fora do escopo; sem log de runId com token |
| T-07-03-04 | Spoofing | banner "ok" falso | mitigate | banner deriva de run.status real do getRun; loading mostra skeleton, nunca "ok" presumido |
</threat_model>
